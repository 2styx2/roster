# What's new

What changed in each Release of roster, the CLI and the app together, newest first: what's new, what changed, what's gone and what's on its way out. The app says once, on its first start after an upgrade, "roster 0.2.0: what's new: `:help news`". [Deprecated names](deprecated.md) lists every old name that still works, and what replaces it.

Each Release has the same sections, left out when empty: **Breaking** (something you have to change), **New**, **Changed**, **Security**, **Fixed**, **Removed** and **Deprecated**. Inside a section the bullets are grouped by area: the CLI, the app, and the `roster serve` API with the API version that brought the change.

## Unreleased

### New

**CLI**

- **FIPS-mode Hosts log in by key: `key_type:` picks the SSH key type** (#436): a Host with FIPS mode on never takes an Ed25519 key, so `roster setup` used to install one it would refuse. Set `key_type: ecdsa` (P-384; or `ecdsa-256`, `ecdsa-521`, `rsa`, `rsa-4096`) at the top level, on `defaults`, a group or one Host. This Box keeps one key per type (`~/.ssh/roster_ecdsa` beside `~/.ssh/roster_ed25519`, the same tag), `roster sync` gives each Host its own type's `IdentityFile`, `setup` installs it (a changed type replaces the old key), and `revoke` takes every type off. `roster setup --host NAME --key-type TYPE` tries one on a Host for a run (beside the line that works); a type change drops the old key only once the new one logs in; `roster hosts NAME` shows a Host's key type and file. `roster check HOST` on a Host that refuses Ed25519 and offers only NIST algorithms says so (199) and suggests `key_type: ecdsa`. Without `key_type:` nothing changes. The Mesh stays Ed25519 for now and leaves such a key Host out (200); `roster setup` never takes a Mesh member's entries off for it (an explicit `roster mesh` does). See [FIPS Hosts](adding-hosts.md#fips-hosts).
- **Stay unlocked: `roster vault unlock` and `roster vault lock`** (#474): a terminal unlock of Bitwarden lasts for that run only, so every `roster run` asked for the master password again, without saying why. `roster vault unlock` asks once and saves the session in `~/.config/roster/bw-session` (0600, written whole, never over a symlink or another user's file), so every roster run on this Box uses it until `roster vault lock` (bw lock, and the file removed), `bw lock`, or the roster app's lock. After a terminal unlock, roster now asks `Keep the vault unlocked for other roster runs on this Box? [y/N]`; No says the unlock lasts for this run only, and an expired saved session says so (bw keeps one unlock at a time, so the app's lock or unlock, `bw lock` or another `bw unlock` expires it). A working `BW_SESSION` in your shell is saved as it is, and the file is never written or read in a `~/.config/roster` someone else owns or may write to. `roster vault status` and `roster check --box` show the saved session (`none (every run asks)`, `saved, working`, `saved, expired`; `saved_session` in `--json`). Bitwarden only for now. See [Staying unlocked](cli-reference.md#staying-unlocked-roster-vault-unlock).
- **Rotate this Box's key: `roster setup --rotate`** (#469): a new key goes on every Host and logs in there alone before the old key's line goes; then the old private key is deleted. A Host it can't reach stays pending with both keys, and `roster check` says so until a re-run finishes it. `roster check --box` warns once the key is older than `key_max_age:` (new, `365d` unless set, or `off`). Runs that change Hosts (`setup`, `revoke`, the Mesh's writes) now go one at a time. Mesh keys are untouched.

**App**

- **`:tutor topology` teaches reach** (#233): the tutorial's demo Inventory has a small, made-up Mesh now, so the Topology tutor's third lesson, "Who reaches whom", lights up what a Host reaches on the map and reads its details: `demo-01` reaches 3 Hosts directly, and `demo-05` is Mesh pending because it didn't answer the last apply. Nothing on the demo connects anywhere. A Plugin's tutorial can use the same Mesh: on the demo, roster serve answers `mesh.status` too (plain, `grouped` and `brief`, as real serve does).

### Changed

**App**

- **The app's fixes say `roster setup --host HOST`** (#461): the Fix for a refused key, an unknown host key or a changed one said `roster setup --only HOST`, which also sets up every Host whose group, type or product is called HOST. With a roster at API 29 or newer (v0.6.0 on) the Fix and its Copy button now say `--host HOST`, that Host alone; an older roster, which has no `--host`, still gets `--only`. The Mesh's details for a Link with no host key now point at the `roster setup` its Why names (serve says the flag its own roster takes).

### Security

**CLI**

- **The saved Bitwarden session checks every folder above it** (#486): `roster vault unlock` checked `~/.config/roster` itself but not the folders above it, and saved by path names, so a `~/.config` others may write to was accepted, and a folder swapped right after the check could put the key elsewhere. Now every folder from your home folder down must be yours (or root's) and not writable by others (unless sticky, as `/tmp`), and the file is made and renamed through one open handle on its folder (Linux and macOS). A refused folder says to fix its permissions (`chmod go-w …`), not to remove it, and a terminal that hangs up while "Keep the vault unlocked …?" waits counts as No. `roster check --box` no longer crashes when `bw status` prints JSON that isn't a status.
- **A usage error never repeats what you typed** (#460): a vault session token typed in the wrong place (`roster --session TOKEN vault op -- whoami`) used to come back on stderr as `invalid choice: 'TOKEN'`, and so did a value in an unknown option (`--session=TOKEN`), an ambiguous one, a number roster couldn't read, a flag that takes none, an unknown `roster help` topic or an `init --inventory` value that isn't one of its forms (a clone URL with a token in it). Now no value you typed is repeated (only roster's own names), whatever argparse's wording around it: the error names the place (`argument COMMAND`, `argument --port`) and what it takes, or the nearest command (`roster hots`: did you mean `hosts`?), and says the value is "not repeated", in `--json` errors too. `--session` typed at roster says that vault bw and vault op take the session from their environment. It still exits 2.
- **Fewer places repeat a value you typed** (#479): `install.sh --inventory` (and `--infra-repo`) no longer prints a value that isn't one of its forms, so a git URL with a token in it, typed without `repo:`, stays off the screen; an unknown option to `install.sh` or `update.sh` is named without its value, and a stray word (a URL with no flag) isn't repeated; `-c PATH` naming no file says "no config file at that path (not repeated)" unless its folder exists and the value isn't shaped like a token (as when an op session token that starts with `-c` is typed as the first word, or a bw key after `-c`), in the error, in `--json`'s `fix` and `path`, in `check --box` and in `inv which`, and shows the path as before otherwise; and the `--session` hint names the vault you typed (`roster vault op -- ARGS` after `vault op`).
- **Still fewer** (#487): `roster -cTOKEN init` (`--blank`, `--inventory`) no longer writes a file named after the token and prints its name: a `-c PATH` that looks like a token is refused, "not repeated", and init makes nothing (init's other messages name the path the way every other command does). A token with dots in it (a JWT, such as an op Connect token, `eyJ….….…`) typed after `-c`, or a token typed as a folder (`-c TOKEN/roster.yml`), is hidden like the others; a `.yml`, `.yaml` or `.yml.example` name is always shown. `--inv NAME` (and `inv use`, `inv remove`) with an unknown name shaped like a token says "no Inventory named that (not repeated)". `install.sh` and `update.sh` cut an unknown option's name at its first character that isn't a letter, digit or `-`, so `--inventory-repo:URL` and `-iURL` no longer print the URL, and one still longer than 20 characters (a glued `-iTOKEN`) isn't repeated.

**App**

- **"roster too old" only for a roster with no `serve` command** (#479): the app said a roster was too old for any start-up error that said both "invalid choice" and "serve"; now only argparse's own `invalid choice: 'serve'` does, and any other one shows as the failure it is, with roster's words.
- **Copy path is left out when roster didn't name the path** (#487): for a `roster.yml` that didn't load because a `-c` value shaped like a token named no file, the error offered to copy the words "(not repeated)".

### Fixed

**App**

- **The Topology map takes the keys back, and `/` starts a new search** (#475): with a Session opened from the map beside it, `:topology` (or `:view topology`, or the map's key) hands the keys back to the map, so a `/` typed next searches the map instead of going to the shell; asking for any open view again does the same. `/` on a map opens its search empty, as the Picker does, so typing a new name no longer adds to the last one.
- **A slow `:help` no longer opens over the terminal you clicked into** (#438): when a guide took a moment to load, clicking into a terminal (or anywhere outside help) meanwhile still let help open and take the keys once the text came. A click now drops the waiting `:help`, as running a command or opening a finder already did; run `:help` again to open it.

## v0.6.0

### New

**CLI**

- **Your Inventory can be a plain `roster.yml` or a team's git repo, both first-class** (#401): roster decides per file, each time it writes. Committed in a git repo with a remote, edits are Pending changes as before. Anything else (outside a repo, no git on the Box, not committed, a repo with no remote) is a plain file: the app's edits, `roster discover --write` and `roster mesh cut` save straight to it, with `roster.yml.bak` beside it, and nothing asks for git or a Publish. `roster check --box` says which. See [A plain file or a team repo](cli-reference.md#a-plain-file-or-a-team-repo).
- **`roster init` gets you an Inventory four ways** (#401): `--blank` (a short, empty `roster.yml` that loads), `--inventory file:PATH` (a copy, once it loads), `repo:URL` (a clone of the team's repo) or `ssh-config[:PATH]` (the Hosts in `~/.ssh/config`: HostName, User, Port and IdentityFile only, wildcards and `Match` blocks skipped, the file never changed). `roster init` alone still writes the commented example. A `roster.yml` already there is kept; `--name NAME` names a new one beside it. See [A new Inventory](cli-reference.md#a-new-inventory).
- **`roster add`: one Host you already know, in one command** (#427): `roster add nas-01 --ip 10.0.0.50 --auth "bw:nas-01 ssh" --group lab` writes it reviewed, through the same code as the app's add-Host form: only its lines added, a team repo's Pending change or a plain file saved in place. A name or address another Host has is refused, naming it. `--from-vault` takes the address and user from the vault item's URI and username, never its password (Bitwarden); it syncs this Box straight after, as `discover --write` does; `--setup` then runs setup and check for it; `--dry-run` shows the lines; it asks in a terminal for what's missing, and `-y` never asks. `roster serve` gets `vault.item_fields` (API 29) for the form to do the same later. See [Adding one Host](cli-reference.md#adding-one-host-roster-add).
- **`roster add --from-vault`: the vault items that aren't in `roster.yml` yet** (#428): with no NAME, it syncs the vault, lists the login items no Login names (the ones new since the last run marked; `--all` every one), and in a terminal walks through adding each one [Y/n/edit/skip], prefilled from the item (`nas-01 ssh` with URI `ssh://10.0.0.50:2200` and username `admin` becomes `nas-01`, `10.0.0.50` port 2200, user `admin`), through the same path as `roster add NAME`, then offers setup for that Host. Bitwarden, 1Password and KeePassXC; never a password (Bitwarden's listing goes through a filter process roster never reads past, decision Q191). `--json` prints the list, `--mark-seen` marks them seen, `--no-sync` skips the sync, `-y` only lists. A locked vault says how to unlock it, never asks. `roster check --box` shows the count from the last run. See [Vault items not in roster.yml](cli-reference.md#vault-items-not-in-rosteryml-roster-add---from-vault).
- **`install.sh` starts you with an Inventory** (#401): with none in the folder it offers the same four ways, a blank one by default (so `--yes` alone makes one, where it used to leave you with none), then `git init` as an option. `--inventory blank|file:PATH|repo:URL|ssh-config[:PATH]` picks one without asking (`--infra-repo URL` still works). One already there is kept, or a new one is added beside it as a named Inventory.
- **`roster vault sync`: what changed in the vault since the last sync** (#430): the vault isn't watched, so roster sees an item added or changed elsewhere only after a sync. `roster vault sync` syncs each vault `roster.yml` uses that keeps a local copy (Bitwarden's `bw sync`; 1Password and the others need none, and it says so), then names the items added and changed and counts the ones removed, from a snapshot of item ids and revision dates in `~/.config/roster/vault-sync/` (0600). Never a password. `roster vault status` says when each vault last synced.
- **`roster vault op -- ARGS`: the 1Password CLI, read-only unless `--write`** (#432): next to `roster vault bw`, with the same rules. op gets your sign-in (the 1Password app, or the `OP_SESSION_*`/`OP_SERVICE_ACCOUNT_TOKEN` in your shell) in its environment and no Bitwarden variable; roster never reads what op prints. `item get`, `item list`, `read`, `vault list`, `whoami` and op's other reads run; commands that change the vault or the account (`item edit`, `signin`, ...) or write a file (`--out-file`, `update`) need `--write`; `op run`, `--session` and `--config` are refused, and so is any command roster doesn't know. See [`roster vault op`](cli-reference.md#roster-vault-op).
- **`roster add NAME --from-vault` works with 1Password** (#432): an `op:` item's URL (from its overview, without any `user:password@`) and username, never its password; several items with that name need its id, as with Bitwarden.
- **`roster help`** (#430): the overview; `roster help COMMAND` a command's options and examples (`roster help vault bw`), `--man` the manual, `--completion SHELL` Tab completion.
- **`roster setup --host NAME`: exactly one Host** (#437): `--only NAME` also takes every Host whose group, type or product is NAME; `--host` takes only the Host by that name. `roster add` now prints `roster setup --host NAME` as its next step, and the fixes `roster check` and the Mesh give for one Host (a host key to record, a key to install) say it too.

**App**

- **`:tutor topology`** (#233): the Topology Plugin ships a tutorial of its own. On the demo Inventory, open the map, show one group, and go from a node to its Host's details and a Session; each step ticks as you do it. The demo has no Mesh, and the tutorial says so.
- **No Inventory yet? The app makes one** (#401): on a Box with no `roster.yml`, **Start your Inventory** offers a blank one, a copy of a `roster.yml` you have, or a clone of your team's repo, in a folder you pick (`~/infra` by default). `roster serve` writes it and names it, and the app starts on it. With a roster older than serve API 28 it says to run `roster init --blank` instead.
- **A plain `roster.yml` says "saved"** (#401): an edit to an Inventory that isn't in a team repo says it was saved to `roster.yml`, never "a Pending change", the toolbar has no Changes button, and `:changes`, `:discard` and `:publish` say there's nothing to publish.
- **The add-Host form fills from a vault item** (#437): with "An existing vault item", **Fill from this item** asks roster for the item's address, SSH port and user (never its password) and fills them in, saying which changed. Needs serve API 29.
- **The add-Host form warns about a taken address** (#437): an address and port another Host already has is said under Address, naming that Host, and the Host can still be added (a second Login to one machine). `roster add` still refuses it (184).

**Plugin API 6**

- **Plugins can know a Session's folder** (#242): with `terminal.read`, each Session from `roster.sessions.list()` has `cwd`, the folder its shell last said it's in (OSC 7), and `command_done` has `cwd`, where the command ran. It's the shell's word, read strictly (a plain `file://` folder, no control or invisible format characters, at most 1024 characters), never checked. [Shell integration](plugins.md#shell-integration).

### Changed

**CLI**

- **A `roster.yml` with no Hosts loads** (#401): a blank Inventory before its first Host, or the last Host removed, is no longer an error.
- **No `roster.yml` found** says how to make one: `roster init --blank`, or the other `--inventory` ways.
- **14 commands to remember** (#430): `init`, `add`, `discover`, `hosts`, `check`, `setup`, `revoke`, `sync`, `run`, `web`, `mesh`, `inv`, `vault` and `help`; everything else is an action or a flag of one of them. `roster check --auth` (was `auth-check`), `roster hosts NAME` (was `info`), `roster hosts --resources` (was `resources`), `roster vault status` (was `providers`; it also shows each vault's state, as `check --box` does, and its last sync), `roster vault reveal NAME` (was `reveal`), `roster vault bw -- ARGS` (was `bw`, the same read-only rules), `roster help --man` (was `man`), `roster help --completion SHELL` (was `completion`), `roster mesh leftovers [--remove]` (was `mesh --find-leftovers`/`--remove-leftovers`). `serve` and `askpass` are run by the app and ssh, so the overview and Tab completion leave them out. Tab completion, the man page, the docs and every fix text name the new forms; `install.sh` writes the new completion line, and `./update.sh` rewrites roster's own old one.
- **Clearer one-line help** (#430): `init` says it only makes a new file (to add Hosts, `add` or `discover`), `setup` that it installs the key on the Hosts not ready yet and syncs (run it again after adding Hosts), `sync` that it touches no Host, `check` one line for each form, `discover --write` that it adds unreviewed Hosts, `vault reveal` that it's for people.

**App**

- **The shell hooks keep their line out of your history** (#242): bash takes its own entry out, zsh starts its history list again from its file without it (only when you haven't typed in the Session yet; a later `:integrate` leaves zsh's history alone and says the line stays there), and PowerShell's PSReadLine keeps it in memory only, never in its history file. It still stays in zsh with `INC_APPEND_HISTORY` or `SHARE_HISTORY` (without `HIST_IGNORE_SPACE`) and with Windows PowerShell 5.1's own PSReadLine.
- **The Sidebar's folder is read strictly** (#242): an OSC 7 that isn't a plain `file://` folder, or one with a control character, an invisible format character (bidi marks, zero-width characters) or more than 1024 characters, shows no folder, rather than a cleaned-up one or the one before.
- **A command's output is kept for `command_done` only while a Plugin listens for it** (#223), not for every marked Session.
- **The app starts lighter** (#405): `:help`'s guides load the first time you open help, `:helpgrep` or Tab-complete a topic, read from the app's own files (never the network), instead of with everything else at start. That takes the JS the app reads at start from about 2.5 MB to 1.5 MB. Every page, topic and search is still there; Tab completes a guide's headings before its text has loaded, and the rare wait past 150 ms says the page is loading.

**`roster serve` API 28**

- `inventory.info` has `store: {kind, note, repo}`: `repo` or `file` (a plain file). For a plain file, every write saves straight to it, `inventory.pull`, `changes.diff` (with `kind`) and `changes.discard` answer that nothing is pending instead of error `70`, `changes.publish` is `90`, and `mesh.cut`'s `change` has a `backup` and `kind`. A git repo with no remote is a plain file now, so its edits are no longer Pending changes. `inventory.create` makes a new Inventory when serve found none (the app's first run): blank, a copy or a clone, named after its folder and made the active one.

### Security

**CLI**

- **A saved Bitwarden session is read only if it's yours alone** (#411): roster no longer follows a symlink at `~/.config/roster/bw-session`, ignores one another user owns or with a second name (hard link), and checks and reads it through the same open file, so it can't be swapped in between. On Windows it checks the file's owner and permissions too: one others may open is ignored with a warning.
- **On Windows, roster never runs a program from the current folder** (#411): `bw`, `ssh`, `git`, `nmap` and every other program roster runs are found on `PATH` alone, so a `bw.exe` left in the folder you start roster from can't run with your vault's session. roster sets `NoDefaultCurrentDirectoryInExePath=1`, so `cmd:` providers and `providers:` commands don't look there either.
- **A mistyped `bw:` Login no longer loads your whole vault into roster** (#443): when a `bw:` reference matched several items or none, roster parsed `bw list items` itself (for no match, the whole vault, to suggest near names), so every listed item's password, TOTP seed and notes passed through its memory; saving a new item did the same for its duplicate check and when bw's answer was lost. Every one of those listings now goes through the same filter process as `roster add --from-vault` (decision Q191): roster reads only each item's id, name, URIs and username, then fetches the one item it needs by its id. The filter passes on login items only, so when a `bw:` reference matches several items and any of them isn't a login (a Secure Note or Card by that name), roster refuses it ("3 vault items match 'db', some of them aren't logins": use the item's id) rather than picking the one login; a note or card by the same name no longer counts as a duplicate when saving. Messages about several items list their names and URIs, no longer the date each was edited, and `roster serve`'s errors 33 and 60 give `revised: null` for Bitwarden. When bw's answer to a create is lost, roster takes the item only if exactly one is named so, and never deletes one it found by name.

### Fixed

**CLI**

- **install.sh finishes on a box with no init system** (#444): in a container (Fedora's, say) with no systemd or `service`, the Auto-update stage said "couldn't find the cron service" and install.sh exited 1. It now starts the cron daemon itself (`crond`, or Debian's `cron`) and says nothing starts it again after a restart; on a box with no cron daemon at all it skips the job, says to run `bin/roster-pull` yourself, and keeps that answer (no-cron in `~/.config/roster/install-choices`), so the box counts as set up and the install exits 0.
- **The Mesh checks ESXi's login before writing its keys** (#445): on ESXi the Mesh's lines go in `/etc/ssh/keys-USER/authorized_keys`, USER as roster.yml's `user:`. When the Host names the login otherwise (`id -un`: another case, a directory account's form), sshd doesn't read that folder, so `roster mesh` (and cut, `mesh leftovers [--remove]`) now leaves that Host as it is, pending, and says why ("esx-02: this login is Root on ESXi, not root (its user: in roster.yml) …"), as `roster setup` and `roster revoke` already did. Before, it wrote a folder sshd never reads.
- **Renaming a Box takes its key with it** (#412): after `box_name:` (or the hostname) changes on a Box already set up, `roster setup` re-tags this Box's key on the Hosts where it already works (`ok    nas-1 (re-tagged)`), and `roster revoke` finds the key under the earlier name too. Both match the line by this Box's own public key, so another Box's line under the old name is never touched. Before, `revoke` looked only for the new name and left the key on every Host. A line's options (`from="…"`) are kept. To rename a Box: set `box_name:`, then run `roster setup`; where it says it found no line (a line you wrote by hand), change that line by hand. Since the key is one per Box, `roster revoke` for one Inventory also takes it off a machine another Inventory lists under another `box_name:`, and says so.
- **A Box's key on ESXi, and renaming onto a taken name** (#435): `roster setup`, its re-tag and `roster revoke` now manage ESXi's own key file, `/etc/ssh/keys-USER/authorized_keys` (the one its sshd reads and keeps across a reboot; a new one gets the sticky bit, as the Mesh's does), where before they only wrote `~/.ssh`, so a revoked Box's key stayed on an ESXi Host. Renaming a Box to a name another Box's key line already has on a Host now stops there (`FAIL  nas-1: [190] another key's line there is tagged roster-managed:NEW …`), as this Box's setup and revoke would take that Box's line too; `roster setup --force` goes ahead. A key line ending in CRLF (a file edited on Windows) is now found by `revoke` and re-tag, two copies of this Box's line become one when re-tagged, setup's 'no line' note names the file it looked in (on Windows, `administrators_authorized_keys` for an administrator), `revoke`'s "To finish" names `~/.config/roster/key-name*` too, and the Mesh's drift warning also sees lines under this Box's earlier name.
- **`roster check` says when another Box replaced a shared Mesh key** (#412): when the Box whose Mesh files a source's are rotates that key or cuts the source, this Box's own lines for the old key stay on its peers until its next `roster mesh`; its `roster check` (and `roster mesh --dry-run`) now warns, per peer, that the line still lets the old key in, from its `from=` address.
- **A Host whose `ip:` is a name gets its network's rate-limiter hint** (#420): when `roster check` gets no answer, the address the name resolved to is matched against `rate_limited:`, so a name in a listed network says to wait a few minutes, and one outside them gets no rate-limiter hint, as an address does.
- **`roster inv add NAME <Tab>` offers nothing** (#420): a new name goes there, so the existing Inventories' names are no longer suggested.
- **A `bw-session` file Windows PowerShell wrote works** (#433): Windows PowerShell 5.1's `bw unlock --raw > FILE` writes UTF-16 with a byte-order mark, which roster read as garbage, so bw failed. roster now reads a session file in UTF-16 or UTF-8 with a byte-order mark as well as plain text, without its line end; a file that isn't a session key (anything but plain ASCII) is ignored with a warning, as a file that isn't yours alone is. The docs give the line that writes plain text: `bw unlock --raw | Set-Content -Encoding ascii -NoNewline $env:APPDATA\roster\bw-session`.
- **Moving a Host to another group keeps its `os:`** (#437): a Host that got `os: windows` from its group keeps it, and a Host moving into a group with `os: windows` gets `os: posix` written on it, so roster never runs the other shell on it.
- **A locked vault with no terminal to unlock it is error 14** (#437), as the app and `roster check` say it, where some commands said 35. Bitwarden (no terminal, or an expired session file) and KeePassXC.

### Deprecated

**CLI**

- **The old command names** (#430): `auth-check`, `info`, `resources`, `providers`, `reveal`, `bw`, `man`, `completion`, and `mesh --find-leftovers`/`--remove-leftovers` still work, hidden, and each prints one line on stderr naming its new form (nothing with `--json`; `roster completion`, run by the rc line at every shell start, says nothing). Change scripts and cron jobs to the new forms: [Deprecated names](deprecated.md#deprecated-in-06).

## v0.5.1

### New

**CLI**

- **Tab completion** (#406): `roster ho<Tab>` completes to `roster hosts`, `roster run <Tab>` lists your Hosts, and options, groups, resources and named Inventories complete too, from the local `roster.yml` only (no network, no vault). `install.sh` turns it on for bash, zsh and fish without asking (`--no-completion` leaves it off) and `uninstall.sh` removes it; `roster completion bash|zsh|fish|powershell` prints the script to add by hand. See [Tab completion](cli-reference.md#tab-completion).

### Changed

**CLI**

- **Which networks have an SSH rate limiter is your setting** (#363): list them as `rate_limited: [10.0.0.0/8]` at the top of `roster.yml` (empty by default), and a Host there that doesn't answer is told its network's rate limiter may be why. - On native Windows, `vault.login` signs bw in with a password or SSO too: it drives `bw login` on a pseudoconsole (ConPTY), where it answered `59` before. **serve API (API 21)**

- `$/cancel {id}` stops a request sent earlier: one still queued or waiting for a lock never runs (code 5, nothing done), a running `host.check` or waiting Mesh run stops its job, and anything else that runs finishes, so nothing is half-written; `vault.lock` is never cancelled. The app's core sends it whenever it gives up waiting. See [Cancelling](serve-api.md#ordering-locks-and-jobs).
- `host.check` runs as a job (kind `check`, one per Host): `background: true` answers at once, `job.progress` says which step it's on, and `host.check_job` has the result (code 49: no such check); the waiting form answers as before. `vault.lock` stops a running check instead of waiting up to 45 s for it. The app checks a Host this way, so a check no longer holds one of serve's workers. Plugins hear check jobs with `serve:host.check_job`. See [Diagnostics](serve-api.md#diagnostics-hostcheck).

Vault items are made one at a time per vault (bw's and pass's CLIs aren't known to take two writes at once).

**serve API (API 20)**

- `roster serve` answers several requests at once: a quick read (the Host list, the Mesh's state, a job's progress) answers while a Publish, a `:check HOST` or a Mesh plan runs, and answers can come back in another order than asked. Writes to `roster.yml` and the vault's lock still take turns, through a lock each; one that waits past its time is the new code 4, with nothing done. Mesh runs and Discover scans are jobs: `jobs.list`, `jobs.stop`, and the `job.progress` notification as they go; serve's exit stops them all at once and records what they didn't do. See [Ordering, locks and jobs](serve-api.md#ordering-locks-and-jobs).

**serve API (API 19)**

- `grouped: true` on `mesh.status` says each meshed group once (`meshed`) and leaves out of `links` the pairs it covers, so a map of 2,000 meshed Hosts gets 2,000 names instead of 98,000 Links. See [The Mesh](serve-api.md#the-mesh-meshplan-meshapply-meshcut-meshstatus).

**serve API (API 17)**

- Mesh jobs: `background: true` on `mesh.plan`, `mesh.apply` and `mesh.cut` answers at once and runs the Mesh in the background; `mesh.job` says how far it has got and how it ended, and `mesh.stop` stops it before its next Host. `brief: true` on `mesh.status` and `mesh.job` keeps the answer small when a meshed group of hundreds of Hosts makes every pair a Link, and marks a `no-via` Link without connecting. Error code 111: a Mesh run while a job runs. See [The Mesh](serve-api.md#the-mesh-meshplan-meshapply-meshcut-meshstatus).

### Changed

**App**

- **`init.lua` is written the Neovim way, in the docs and examples too:** [Your init.lua](app/config.md#writing-initlua) opens with how to write one (a one-file Config, one split into `lua/` modules, how errors and `:options` point at the module and line, `:help options`, `:config types`, and checking for a newer name before using it), and every snippet in it, the recipes and the keyboard guide is `roster.o` lines and `roster.*` calls. `examples/init.lua` is one `roster.o` line per option, so the file `:config` makes lets you uncomment any line on its own (its header now says `:source` applies it), and `examples/init-split` is a whole Config in modules. `:config import-terminal` writes `roster.o.terminal.size = …` lines instead of `roster.set` calls, still between its marker lines. A returned table still loads and still wins over the calls ([The returned table](app/config.md#the-returned-table)).
- `roster.themes.define` of an id that's defined already is an error naming both lines, where the later call used to win: change a Theme with `roster.themes.update(id, fields)`; a Config that defines one Theme in a base module and again in an override changes the second to `update` (see [Deprecated names](deprecated.md)). `roster.set` checks the option's name at its line, with the name meant, rather than once the file has run. See [The `roster` table](app/config.md#the-roster-table).
- **A quieter message line, as Neovim's:** errors, warnings, answers (`:info`, `:config path`) and results that need attention (a Publish, a save roster warned about) still show, but a routine action's confirmation (a Host saved, added, moved or renamed, "Reloaded init.lua") and a toggle's tip ("Sidebar hidden, and kept that way. modes.standard.sidebar = false in init.lua makes it the default") no longer do: you see what changed. `:messages` lists the recent ones, quiet ones too; `:messages all` brings them back to the line (the app remembers it), or `ui.messages = "all"` in `init.lua`, which wins. A screen reader still hears what changed. See [`ui.messages`](app/config.md#fonts-and-the-terminal).
- **Plugins are quiet like roster:** a Plugin's info notice ("Copied esx-02's address") no longer pops up unless `ui.messages = "all"`, and a Plugin marks a routine confirmation on the message line quiet with `roster.echo(text, { quiet = true })`, as Folders now does for "Added esx-02 to Lab". Warnings, errors, answers and a notice with buttons still show, a screen reader still hears the quiet ones, and `:messages` keeps them all, notices too. `:cancel`'s "Stopping …" is quiet as well: the progress itself says it's stopping. A notice that needs attention says `{ quiet = false }`. Plugin API 4. See [`roster.echo`](plugin-api.md#rosterechotext-opts) and [`roster.notify`](plugin-api.md#rosternotifytext-level-opts).
- A Plugin's error about data that can't be handed over names the function and where in the table (`roster.sidebar.set: rows.3.label: a thread can't be a Plugin value`), and every `remove` checks its id as `set` does. `session_exit` names the Host of a tab closed while its Session ran.
- A command line a Plugin hands over (a row's, a button's, a finder item's, a status segment's) runs only if it's one of that Plugin's own commands or one of [the few of roster's a Plugin may run](plugin-api.md#command-lines-a-plugin-may-run): a button can no longer run `:plugins grant …` whatever its label says. `roster.sessions` is there for every Plugin now (for `show`); `roster.sessions.open` still needs `sessions.open`.
- A Plugin's key binding (`roster.keymap.set`) runs its line through the same check as a button's, each time the key is pressed: a key can't run `:plugins grant …`, `:packages`, `:source` or another Plugin's command. `:keys` shows such a binding as `plugins run NAME LINE`. See [The `roster` module](plugins.md#the-roster-module).
- A Plugin granted `serve:changes.diff` or `serve:host.check` gets a `cmd:` or `env:` Login reference cut to its kind in the diff's text and the check's messages too, as it already was in an `auth`: `cmd:` to the end of its line, `env:` without the variable's name. roster's own Pending changes and Health pages still show it whole. See [Security](app/security.md#plugins).
- A Plugin's progress shows in Focus too, in the top-right corner (it was hidden with the status bar), with its stop button. With several at once in a narrow window, the latest keeps its title and the others show only their track and share. See [Plugins](plugins.md#asking-progress-the-toolbar-and-going-places).
- A click or a timer from before a Plugin was reloaded can no longer run one of the reloaded Plugin's functions: each load's functions have numbers of their own. A table's actions that `roster.views.update` replaced are dropped at once.
- The Picker's ⓘ shows on the selected row only, as a Sidebar row's buttons do: a row under a resting pointer no longer shows one too.

- `terminal_output` sends the lines a Session's terminal commits, read from a terminal of its own, instead of the raw output with a one-second repaint filter: a progress bar arrives as it ended, a wrapped line comes whole, the screen ConPTY prints again after a resize is never output, and what full-screen programs (`vim`, `top`) draw isn't sent. See [Events](plugin-api.md#events).
- In a Plugin, `pairs` visits keys in order (numbers, then text), so the same state makes the same changes on every machine. An empty table reaches the app as `{}`, which it takes as an empty list.
- A Plugin's Leader key that's taken is refused with a notice naming what has it and a few free keys like it (`␣ f is taken (by builtin: find). Free after the Leader: a, g, h`).
- Folders is a built-in Plugin on the public API now, like the Host count: `:plugins` lists `folders`. It works as before (`␣ a`, `␣ A`, `:folder`, drag and drop, init.lua's Folders), and keeps your Folders in its own data folder instead of `folders.yml`. At the first start, `folders.yml`'s Folders move in, every Host included; one that doesn't parse moves nothing until it's fixed. After that the app doesn't read or write `folders.yml`: `:check` says so, and you can delete it. A Folder that was folded stays folded (its id is `folders:NAME` now, and the old one still works with `:fold`). See [`folders.yml`](app/config.md#foldersyml).
- A Plugin whose manifest, `init.lua` or a module is a symlink (or a junction) leading outside its folder doesn't load, for a local Plugin and a Package alike. See [A Plugin's files](app/errors.md#a-plugins-files).
- `init.lua`'s `modes` no longer warn "no section named …" or "no segment named …" for a Plugin's section or status segment: the names are checked once the Plugins have loaded.
- A Plugin's finder can have a `prompt` of its own (`Folders ›`); without one it shows its title, once (finders with items showed `›` twice). See [`roster.finders.set`](plugin-api.md#rosterfinderssetid-finder).
- A Plugin waiting for roster serve (behind a Publish, say) is no longer given up on and disabled after two seconds: waiting for serve never counts against a Plugin, for that call or for the calls queued behind it (`:help plugins`).
- Discover and Topology take `leader = false` in their `config`, as the Mesh controls do: they bind no Leader key, and the command (and Discover's **Scan**) still works. See [discover](../plugins/discover/README.md) and [the Topology view](../plugins/topology/README.md).

**CLI**

- `ROSTER.md` tells Claude to run `roster check <name> --json` when a Host doesn't respond, to see which step fails and its fix, rather than `roster check --only <name>`.

### Security

**App**

- A Plugin can act on the network or the Inventory only when you've just asked it to: every serve method the install prompt flags (`mesh.apply`, `mesh.cut`, `host.check`, `discover.start`, `discover.add`, …) and `roster.inventory.update`, `.rename`, `.move` and `.review` work only in an action, command, finder item, toolbar control or question's answer of its own. At load, on an event or from a timer they're now errors (only `discover.start` and `discover.add` were held before). See [Plugins](plugins.md#asking-roster-serve).
- Only what you chose counts as your call: a finder's items as it opens, a `:check` section's lines and a question's cancel when another Plugin's question replaced it can no longer copy, ask, run a command line or call those methods, so another Plugin opening a finder can't lend them your call.
- `cmd:` and `env:` Login references are now cut from roster serve's error messages to a Plugin too, not only its answers.
- `roster.cmd` holds a command named after one of roster's (`open`, `check`, `plugins`, …) to roster's rule even if the Plugin added a command of that name.
- A Plugin can no longer keep your call alive by running its own commands through `roster.cmd` one after another: the command `roster.cmd` runs from your call is still your call (one hop, as a `roster.serve.request`'s answer is), but a `roster.cmd` or request made in it isn't, so the next command can't copy, ask, run a command line or act on the network. Folders' drag and drop still works. See [Plugins](plugins.md#asking-progress-the-toolbar-and-going-places).
- The `job_progress` event is cut as roster serve's answers are: a `cmd:` or `env:` Login reference in a job's text (a failed check's error message echoes the Login) reaches a Plugin as `cmd:` or `env:`. The cut reaches an answer's keys now too, not only its values.

**CLI**

- On Linux and macOS, `roster serve` removes its askpass folder (the private password socket's) however it ends: closed stdin even mid-request, SIGTERM, SIGHUP or SIGINT. A serve killed outright can't, so the next one to start removes this user's folders whose serve is gone, never another user's, a live one's or anything a link points at. Windows has no such sweep: the password pipe ends with serve whatever happens, and a folder a killed serve leaves under `%TEMP%` holds only Quick Connect's public host keys. On Windows serve also checks each askpass pipe client's process is yours, on top of the pipe's permissions.
- A Host check stopped while it logs in (`vault.lock`, `jobs.stop`) ends that login's ssh, so locking no longer waits up to ~35 s behind it.
- `--json` cuts `cmd:` and `env:` references everywhere in its output: in a key as much as a value, and in a value that isn't plain JSON (a set or a path), which went out uncut.

### Fixed

**CLI**

- A Mesh source moved back to roster's own directory (its `mesh_dir:` removed) that still holds the key from before the `mesh_dir:` gets a warning that roster uses that old key again, with `roster mesh --rotate HOST` to replace it; it was used again without a word. See [`mesh_dir:`](mesh.md#esxi).
- On native Windows, closing `roster serve` during a Mesh run ends the run's ssh with everything it started, as a step that times out does, so `mesh.json` records which Hosts were left to do (an ssh that is a batch file kept running before).
- The Mesh no longer writes a `via:` Link whose jump Host this Box has no host key for: the source's own Link to the jump Host isn't written then, so `ProxyJump` would have named a Host its ssh config doesn't have. Both are `no-host-key`, and `roster check` fails until `roster setup --only HOST` records the key.
- `roster discover --json` with a broken `roster.yml` found without `-c` (`ROSTER_CONFIG`, or the usual places) is error `1` with its fix, where it was ignored silently; with none at all it still scans.
- `roster serve` started with a temp dir whose path leaves a Unix socket's no room puts its askpass folder in `/tmp` rather than fail.
- `roster discover` scans IPv6 networks (nmap takes them only with `-6`, in a run of their own), scans an address that two of its networks hold once instead of writing it twice, and counts the hosts that answered with none of the ports open, as it said it did (nmap ran with `--open`, which leaves them out).

**App**

- `init.lua` runs as a block, as Lua runs a file: a one-line `require("me")` of a module that only makes `roster.*` calls loads, where it failed with "init.lua must return a table (it returned a boolean)" unless the file had a second line. `return require("me")` of a module that returns nothing says what happened and what to do. A bare `{ … }` with no `return` is now a syntax error at its line. See [How it works](app/config.md#how-it-works).
- Among `roster.*` calls the last one wins, so a module of overrides required after a base module takes effect (the first call won before). The returned table still wins over calls. See [The `roster` table](app/config.md#the-roster-table).
- A Config error in a value a required module returns names that module and line (`lua/opts.lua:4: …`), and one roster can't place says `(line unknown)`; it gave `init.lua` with a parent key's line, or the line of a `roster.set` whose value the returned table had replaced.
- A Plugin call that fails no longer leaves the buttons it was replacing dead ("that action is gone"), nor timers and commands behind it; 100 failed calls could use up a Plugin's timers.
- A Plugin that asks roster serve in a loop gets an error after 100 calls (or 300 s of waiting) in one go, instead of running for ever and keeping serve from the app.
- An answer to what a Plugin asked while loading is no longer lost (first load) or put on the load before (reload).
- A Plugin command whose line runs itself, or two that run each other, stop with a notice instead of recursing until the app gives up.
- A Plugin's `pairs` costs far less on a list (about 7 times faster on 10,000 items) and on tables with only text or only number keys, in the same order as before.
- The install prompt says what `serve:host.check` does: it connects to the Host and signs in once, changing nothing there or in the Inventory (it said it could change things on your Hosts). And a Plugin's command named after one of roster's (`:theme`, `:lock`, …) is never its own to run with `roster.cmd`, whichever of roster's it is, not only the ones that change trust or writes.
- Closing the app gives `roster serve` up to 3 s (was 1 s) to stop a running Mesh job and record what it didn't finish before it's killed.

**serve API**

- `host.check`: a waiting check that had joined another request's check answers `5` as soon as it's cancelled, rather than keep its worker until that check ends (up to 45 s); the check goes on for the others.
- `host.check` (API 22): a waiting check cancelled stops the check only when no other request waits for it and none asked for it in the background, where cancelling a request that had joined someone else's check stopped it for both; the background form says whether it `joined` a running check, and the app's core stops only a check it started when it gives up on it. A check asked for while the last one is stopping is a new check, not the stopping one (which answered `ok: false` with its steps skipped). `host.check_job` still finds a check that ended after a newer check of its Host started (it was `49`). A check shares the vault only for the steps that fetch a secret or mint a token, so an unlock or a lock no longer waits up to 45 s for a check (the lock screen hung, then failed).
- `vault.undo_create`: an undo that fails in an unexpected way keeps the item, so it can be undone again (it was forgotten: the item stayed in the vault and a retry answered `63`).
- `vault.configure` no longer fails ("dictionary changed size") when roster.yml reloads with a new provider while it runs.
- Closing `roster serve` mid Mesh job stops the job at once and records in `mesh.json` what it didn't finish (pending), where the job died with serve and the next run didn't know; a step cut short leaves each file whole.
- `discover.*`: IPv6 targets scan (with `-6`), a scan of IPv4 and IPv6 targets together no longer fails sorting them, an address two targets hold is visited once (`targets` drops the one another covers), `quiet` counts the Hosts that answered with none of the ports open (nmap; it's 0 with the built-in scanner, which can't tell them from no Host), and the built-in scanner reads its Hosts' SSH banners at once rather than one by one, so a batch (and a stop) no longer waits minutes.
- A background `mesh.plan` or `mesh.apply` works the Mesh out once rather than three times, two of them while serve answers nothing else.

### Deprecated

**App**

- `folders.yml`: Folders made in the app are kept by the Folders Plugin now. It's read once, to move its Folders in, and then no longer; hand-written Folders go in `init.lua`. See [Deprecated names](deprecated.md).
- `roster.keymap.set(context, keys, false)`: use `roster.keymap.del(context, keys)`. It takes the Plugin's own binding off now, rather than claiming the keys with no action. See [Deprecated names](deprecated.md).
