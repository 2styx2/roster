# Security model

The roster app keeps roster's promise: **secrets are fetched when needed, kept in memory, and never written, printed or shown.**

## Where a password goes

| Step | Holds the secret? |
|---|---|
| Vault (Bitwarden, …) | yes, at rest |
| `roster serve` process memory | yes, while unlocked |
| Private askpass socket (a user-only named pipe on Windows), one-time token | yes, in transit, once |
| Session process env (the token only, never the password) | the token, for the Session's life |
| `roster askpass` → `ssh` | yes, in transit |
| Rust core | **never**, except a prompt fill (the owner's ruling): once, in transit, straight into the Session's PTY, then wiped ([below](#filling-a-password-prompt)) |
| Frontend, app State, Config, logs | **never** |
| Terminal output and scrollback | **never** (ssh reads the password itself; a filled prompt doesn't echo, or nothing is typed) |

A few exceptions are typed by you and leave the UI straight away:
- **The master password:** sent once to `vault.unlock`, and the field clears. Bitwarden turns it into a session key and roster drops it. KeePassXC (ticket 25) has no session: `keepassxc-cli` opens the `.kdbx` again on every call, so `serve` keeps the master password itself in memory until `vault.lock` and gives it to each `keepassxc-cli` call on its stdin, never on a command line or in an error.
- **A Quick Connect password (ticket 14):** it lives only in the connect card's masked input (never React state, the tab store or the State), which empties the moment Enter sends it. The Rust core moves it into `quick.prepare`'s request to serve's stdin and drops it. serve holds it under a one-time askpass token, exactly like a vault password: spent on ssh's first password prompt, gone after 60 s unused (the channel prunes expired tokens) or at `vault.lock`. It never appears in a response, an error, serve's log (which names the Session, `root@10.0.0.5`, only), an argv, `roster.yml` or the known hosts. Left empty, the Session logs in with this Box's own keys (`BatchMode=yes`).
- **An `auth: prompt` Host's password (ticket 16):** typed into the pane's connect card the same way (its own masked input, never React state), sent once in `session.prepare`'s request through the Rust core to serve's stdin, and held under a one-time askpass token like a Quick Connect's.
- **"Save to vault" on a typed password (tickets 15, 16; decision Q68):** ticking it under the password field (Quick Connect, or an `auth: prompt` Host) asks serve to keep that password in its memory after ssh has it, bound to the Session's id (`held`). The app only ever has the id: the save call (`quick.save`, `host.save_login`) names it and never sends the password again. serve saves it only once that Session has logged in with exactly it (Q43): ssh runs serve's logged-in script as its `LocalCommand`, which OpenSSH does only after authentication, and the script reports the Session's own askpass token; a report counts only if that token handed this password to ssh, so a box that let ssh in without asking (or a report from anywhere else) proves nothing. The script learns it's a report from an env var it sets itself, never from an argument (an askpass argument is a prompt, which the box chooses). serve forgets the password after one save, when the app says the Session ended or the offer was turned down (`vault.forget_typed`), at `vault.lock`, and 10 minutes after it was typed, whichever comes first. A failed save (a taken name) keeps it, so another name can be tried. Without the tick nothing is held: it's spent like any askpass password. It never appears in a response, an error, the log (`askpass: root@10.0.0.5: logged in`), an argv, `roster.yml`, the Pending change or the known hosts.
- **Signing in (ticket 31):** the master password, a two-step or new-device code, or an API key's `client_secret`, each sent once to `vault.login`. The field empties as soon as the call returns. roster gives them to `bw` through an env var or `bw`'s own prompt, never on a command line. It holds the master password only for the sign-in's life, so it can restart `bw login` after a wrong code. That ends when the sign-in is done, cancelled or locked, or after 10 minutes idle. The app cancels a started sign-in whenever it's left other than by going on: Esc, a failure with no step to carry on from (a timeout, a refusal), or the lock screen going away. None of them ever reaches React state, the Rust core's logs or an error message.
- **A new Host's password (ticket 11):** typed into the add-Host form, it lives only in its input (never React state) and is sent once to `host.add`; the field empties when the call returns, pass or fail. roster uses it for the one test login, then saves it as the Vault item (`bw create item` on stdin) and forgets it. It never appears in a response, an error, stderr, `roster.yml` or the Pending change.

## No vault of our own

The roster app never stores secrets: there's no built-in vault, now or later (decision Q40). Passwords live in the user's password manager: Bitwarden, 1Password, `pass`, or KeePassXC for local-only use (Q41). roster fetches a password for one use and forgets it.

## Locking

- Unlocking the vault is what unlocks the app. There is no separate app password.
- It locks after 15 minutes idle (configurable), or on demand with the leader key plus the lock key, or `:lock`.
- Locking calls `vault.lock`. That forgets the vault session key (or KeePassXC's held master password), every cached secret and every askpass token, and runs the provider's own lock. A running Host check is stopped at its next step; it shares the vault only while a step fetches a secret or mints a token, keeps no secret between steps, and so never holds the lock (or an unlock) up for the rest of its 45 s. A check stopped during its login ends that login's ssh (decision Q119), so the lock doesn't wait for it either.
- Sessions keep running while locked, with their content hidden until you unlock.
- The app always opens locked. If `roster serve` is still unlocked when the window (re)loads, the app calls `vault.lock` first.
- Idle means no key, click, pointer move or wheel anywhere in the window. The timer runs in the frontend (`app/src/lock/idle.ts`), where that input arrives, so no keystroke has to cross to Rust. It re-checks the clock when it fires, so a late timer (sleep, a throttled window) still locks.
- If no Host Login uses a vault with a master password (`vault.status` says `unsupported`), there is nothing to unlock, so there's no lock screen and no idle lock, and the lock key says "nothing to lock".
- **Signing out (ticket 42):** "Use a different account" under the unlock form, or `:vault signout`, asks first ("Sign out of you@example.com on this Box?"), then calls `vault.logout`. serve runs everything `vault.lock` forgets **first** (askpass tokens, typed passwords held for "Save to vault", every cached secret, a sign-in in progress, the session key, KeePassXC's held master password), and only then `bw logout`, so a CLI that then fails leaves nothing behind. The app locks before the call goes out and shows the full sign-in form after it. The account's email and server are shown (they aren't secrets); no secret is in the call, its answer or the log. Providers with no account (KeePassXC, `pass`, `env`, `cmd`) have no sign-out: the link is hidden and the command says why.
- If the vault CLI is missing or not logged in, the lock screen says what to install or run (roster's message) and offers "Check again". It doesn't ask for a password it can't use.
- If an unlock fails without a clear answer (the call timed out, or `serve` was lost), `serve` may still finish the unlock. The app stays locked, asks `vault.status` (it shares the vault's lock, which the unlock holds alone, so it answers after that unlock; a serve before API 20 answered in order, which did the same), and calls `vault.lock` if it says unlocked, unless a newer unlock attempt has started meanwhile.
- The master password lives only in the lock screen's input (never in React state). It goes to the `vault_unlock` command and the field is emptied as soon as the call returns. The Rust core passes it to `serve`'s stdin inside the request and drops it; it's never logged or put in an error.

## The askpass token

`session.prepare` hands back a one-time token (60 s, spent on first use) in the Session's env. The Rust core sets it on the Session's process and never in an argv: a command line is readable by any process and logged by process-creation auditing for the process's whole life, while the environment is only readable by the same user. On WSL that means setting it on `wsl.exe` and naming it in `WSLENV` (`docs/app/dev/tauri-pty-wsl.md`, section 2). It never appears in Debug output or error text: names only, and spawn errors are redacted.

**The socket's folder (ticket 113, decision Q119).** On Linux and macOS the channel is a Unix socket (`0600`) in a fresh `0700` folder, `roster-askpass-PID-…`, and serve checks each peer's uid as well. serve removes the folder however it ends: stdin closed (even mid-request), SIGTERM, SIGHUP or SIGINT. Only SIGKILL or a dying interpreter can leave one, and nobody else can reach it then either (its socket has no listener, and the folder is still the user's alone). A starting serve removes the folders of this user whose serve is gone and whose socket doesn't answer, through descriptors opened with `O_NOFOLLOW`. It never touches another user's folder, a folder with anything in it that serve doesn't put there, or what a link points at. Windows isn't swept: the pipe there ends with serve however serve ends, so nothing that leads to a password is left, and a folder left under `%TEMP%` holds only Quick Connect's public host keys.

**Native Windows roster (ticket 19, decision Q78).** The channel is a named pipe instead of a Unix socket. Windows has no `0700` folder for a socket to hide in, so the pipe carries its own security: owned by the user's SID, with a protected DACL whose only entry is that SID (no Administrators, no SYSTEM, nothing inherited), remote clients refused, and a name with 128 random bits that serve claims first (`FILE_FLAG_FIRST_PIPE_INSTANCE`), so nobody can create it beforehand and listen in. The helper opens it with identification-level impersonation only, and serve checks each client's process is this user's (its token's user, through `GetNamedPipeClientProcessId`) on top of the DACL, refusing one it can't tell (ticket 63). Another user on the PC, or a network client, can't open it; the token in the Session's env is still needed by anyone who can. The helpers are `roster-askpass.exe` and `roster-askpass-login.exe`, installed with roster (Windows' ssh runs a program, not a script). Quick Connect's known-hosts file sits in a folder under `%TEMP%`, which only the user (and administrators) can open.

## Filling a password prompt

When a Host Session waits at sudo's password prompt, the fill key (`␣ p`, the `fill` command) types the Host's password from the vault into it (ticket 119, decision Q129). Nothing is typed until you press it, and it's offered only while the line at the cursor is sudo's prompt for the Session's login user. The rule throughout: **fill only a prompt that is provably this Host's own, and refuse whenever in doubt.** A refusal costs a typed password; a wrong fill hands this Host's password to another machine.

**Where the password goes (the one exception, the owner's ruling).** The vault, `roster serve` (`session.fill`, the one serve result that holds a secret), the Rust core, the Session's PTY. The core may hold a secret for this and nothing else: the PTY lives in the core (on Windows a ConPTY in the app's process while serve runs in WSL, so serve can't reach it), and a PTY takes input only from its owner. The frontend sends only the Session's id and the prompt line it read off the screen, and hears back only the Host's name: the password never reaches the webview, React state, the State, `:messages`, a log or an error. The core holds it for one call (`SessionManager::fill`) in a type with no Debug value, no Display and no Serialize, writes it with Enter in one write, and overwrites its bytes as it drops it; copies on the way in (the JSON line serve answered with) aren't overwritten. A Plugin can't ask for it: its serve allow-list has no `session.*`, and the `fill` command isn't one a Plugin's `roster.cmd`, key or button may run.

**Which prompts.** Only ones that say whose password they want, and only when that's this Host's own Login:
- `[sudo] password for USER:` where USER is the Host's ssh user: its `sudo: {auth: REF}` from `roster.yml` (a vault reference, never a value, never `prompt` or `agent`), else its ssh Login;
- `USER@HOST's password:` (a nested ssh) only for the ssh user at the Host's own name or address in serve's check; `localhost` is refused, since through a tunnel it may be any machine. The app offers it only for a nested ssh it can follow ([A nested ssh](#a-nested-ssh)), with the Host that ssh went to.

A bare `Password:` is refused: su asks for root's, a login or telnet for anyone's, a nested keyboard-interactive login for another machine's, and none of them says which. So su is never filled.

**The Session must still be on that Host.** `session.prepare` says what each Session connects to (address, port, user), the core keeps it, and the fill sends it back: serve refuses (130) when the Host has been edited since (a new address, port or user may be another box). The Host is the one the core recorded when the Session opened; the frontend can't name another. A Quick Connect has no Login, so nothing is offered.

**Did you leave the Host?** With the shell's OSC 133 marks (shell integration, or roster's opt-in shell hooks), the app offers the fill only while the command running is sudo itself (after any `VAR=value`), running nothing that reaches another machine (`sudo -u x ssh …`, `sudo docker exec …`, `env`, `time`, a pipeline: refused), and only while that command has printed nothing but sudo's own lines (its prompt, "Sorry, try again."); so `sudo -i` is filled at its first prompt but not once its shell has run something. The command line is read off the terminal's screen where the shell's `C` mark says it ends, so history recall and redraws are what you see. At the shell's own prompt nothing is offered, and with marks that aren't roster's, once a marked shell starts inside a command roster stays unsure for good. The marks come from the Host too, so they can only take the offer away, never allow a fill on their own; only roster's own marks, with the Session's token, say which shell they're from ([Which shell asked](#which-shell-asked-rosters-own-marks)). **Without marks roster can't tell whether you've left the Host**: a `sudo` prompt on another machine you reached with a key looks the same, and filling it would hand that machine this Host's password. The offer says so in words ("roster can't tell whether you're still on esx-02").

### Which shell asked: roster's own marks

Every fill turns on one question: is the prompt under the Session's own shell, or under something it ran that reached another machine? Marks (OSC 133) answer it only when they're roster's own (ticket 120, decision Q131). roster's shell hooks put a **token** on every mark: 96 random bits, new for each Session attempt, living only in that shell process. No other machine sees it (an ssh's far Host gets none of the first Host's shell), so a mark with it is provably the Session's own shell's, and any mark without it is another shell's or forged. The token counts only when the hook line can only have reached the Session's own shell: sent before anything was typed, or while the marks showed that shell at its prompt with nothing run that may reach another machine. Plugins never see it: from the hook line going out until roster's first own prompt, nothing the Session prints reaches them (that's the line's echo), and after that the token is dashed wherever it shows, even wrapped across lines.

- **With roster's marks:** a command starts at the shell's own `C` and ends at its own `D`, however it ended. sudo is offered while that command is sudo itself; afterwards, at the next one, again.
- **With marks that aren't roster's** (your shell's own integration): once a command that may reach another machine has run (`ssh`, `mosh`, `telnet`, container and cloud shells, serial consoles, `screen`, `tmux`, a shell, `su`, `sudo -i`, `eval`, `$(…)`, and more), roster can't tell which shell any later mark is from, so it fills nothing more in that Session, its own sudo included, and the note says to reconnect with roster's shell hooks on (`shell_hooks`, or `:integrate` before you ssh). The list is best effort: an alias or a script that runs ssh isn't caught, since roster reads the line, it doesn't run your shell. roster's own marks are the reliable path.
- **Without marks:** sudo's exact prompt only, and the offer says roster can't tell whether you're still on the Host: a nested shell can't be ruled out.

### A nested ssh

When you run `ssh esx-02` (or an Inventory Host's address) inside a Session **with roster's own marks**, roster follows it. With other marks or none, nothing nested is offered, and a nested ssh's password prompt gets a note saying why.

- **Where it went.** The command line is the one read off the screen at the shell's own `C` mark, and only a line you pressed Enter on. roster reads it with ssh's own rules for the common flags (`-l`, `-p`, `-o User=/Port=/HostName=`, `user@host`, clustered flags, options after the destination) and refuses anything it can't follow fully: `-J` and any jump host, `-o ProxyCommand` and every `-o` that changes where ssh connects or how it checks the host key, `-F`, `-S`, a quote or `$`, a wildcard, two users or two ports. What's left is matched against the Inventory by name or address and port; no match or two matches is no Host, and `localhost` never is.
- **Where you are.** The Session's row (and its tab) shows the Host it's on now, `esx-01 ─ esx-02`, until the first Host's own shell marks the ssh's end, however it ended. A mark from the far Host never ends it. It's what roster believes, never by itself a reason to fill.
- **Its login.** Offered only while that ssh is logging in: the prompt is exactly `USER@HOST's password:` for the user and host that ssh uses; that Host's Login has a saved password (a key or agent login types nothing; agent forwarding stays your flag, roster never turns it on); you haven't typed into the ssh since it started (answering a host-key question counts, and that question is never answered for you); nothing but ssh's own retry line after its first prompt; once per ssh. serve (`session.fill`'s `hop`, API 26) checks the Session's own Host as before, then that the Host the ssh went to is reviewed and still has the address, port and user roster resolved, and the core types it only if the Session's output ends with that very prompt, the cursor right after it (read as text, so colours and ConPTY's cursor moves don't hide it), after the same no-echo probe. The core never sends a nested fill to a roster serve too old to know which Host it's for. A key you type takes the offer away at once.
- **Its sudo.** That Host's `sudo:` (else its ssh Login) is offered at sudo's prompt only at the first command its own marked shell runs. Once a command there has ended, what it ran could have reached a deeper machine that marks like that shell, so roster refuses for the rest of that ssh.

**The limits, honestly.** roster can't see the first Host's ssh config or DNS: a name may resolve differently there, and a config can set a port or a jump host without the prompt showing it (a config's `HostName` does show, and is refused). ssh's host-key check on that Host is what ties the name to a box, and because a first connection's host-key question needs your `yes`, a typed key, roster never fills a login to a Host the first one didn't already know. The first Host knows the token (it's its own shell), so a first Host that's been taken over can draw a whole fake `ssh esx-02` and prompt; it already sees everything a real nested ssh carries, and the same fake would collect a password you typed by hand; the note names the Host roster thinks it is. The far Host never knows the token, so it can't make roster think you're back on the first one.

**It must not echo.** A prompt that echoes would put the password on screen, in the scrollback, in what `terminal.read` Plugins get and in the frontend's terminal. Before the password the core types a probe: Ctrl+U, a letter, Ctrl+U. At a prompt that doesn't echo (the terminal's line discipline with echo off, as sudo sets it, at every hop of a nested ssh) nothing is printed and the line ends up empty, which also clears anything you'd typed there. At one that echoes, the letter comes back. If the Session prints anything from the moment the fill starts (the vault lookup included) until 800 ms after the probe, or you type a key meanwhile, the password isn't typed and the message line says why. A tried prompt isn't offered again until the Session shows a new one, so a second press can't type it twice.

**The limits, honestly.**
- Without marks, see above: the offer is all that stands between a fill and another machine's sudo prompt. Turn on roster's shell hooks where that matters; your shell's own integration makes roster stop filling once something that may reach another machine has run.
- An echo slower than 800 ms (a link that slow) would come after the check.
- sudo's `pwfeedback` prints a `*` per key, so it counts as an echo and isn't filled. A custom sudo prompt (`sudo -p`, `passprompt`) isn't sudo's prompt to roster, and isn't filled.
- A program that reads the password itself with echo off and then prints it, or one on a Host that's not yours, gets what it asks for: the probe only shows the prompt doesn't echo.
- A compromised webview could press the key for you, as it could already type anything into any Session; the Content Security Policy is what keeps it from being compromised.
- The vault's own cache in serve is unchanged (secrets are cached while unlocked, forgotten at lock). A locked vault shows the lock screen; press the key again after unlocking.

## The webview

The built app runs under a Content Security Policy (`app/src-tauri/tauri.conf.json`): `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'`. So no remote script, style, font or connection, no inline script and no `eval`. Tauri adds hashes for its own inline scripts. `style-src` keeps `'unsafe-inline'` for the `<style>` elements xterm.js creates, and `dangerousDisableAssetCspModification: ["style-src"]` stops Tauri from adding a style nonce, which would void `'unsafe-inline'`. Fonts (Inter, Iosevka) are bundled, never fetched. On desktop, `tauri dev` loads the Vite dev server directly and Tauri adds no CSP header there (only to embedded assets), so HMR needs no `devCsp`.

**Web services (ticket 18, decision Q71).** Host details and `:open SERVICE` hand a service's URL from `roster.yml` to the OS's default browser, never to the webview. Only http and https URLs with a host and no user or password in them are opened, checked in the frontend (`details.ts webUrl`) and again in the Rust core (`roster-core browser.rs`) by one rule both test on the same table of cases (`crates/roster-core/tests/fixtures/web-urls.json`): printable ASCII only, no `"` or `\`, the scheme written `http://` or `https://` exactly (lowercase, both slashes; nothing is normalised), and a port of 1 to 65535 if there's a colon. The core passes the URL to ShellExecute (Windows) or `xdg-open` as one argument, never through a shell. A URL never carries a secret: logging in to the web UI is the browser's business, and the panel shows a Login only as its vault reference (the Vault item's name). A password someone wrote into a URL in `roster.yml` is drawn as `•••` and that URL isn't opened.

## Connections

- Unreviewed Hosts are never connected to (the same rule as `roster run`).
- Key-enrolled Hosts use `BatchMode=yes`, so a broken key fails instead of falling back to a password prompt.
- Host keys come from what `roster setup` recorded. The askpass helper refuses host-key prompts, so a mismatch stops the connection.
- Quick Connect shows the scanned fingerprint and asks you to confirm before connecting (decision Q67). `quick.prepare` fetches the key again and goes on only if it's exactly the one shown (else 23); a key that differs from one roster recorded for the address is refused (43), never asked about. The confirmed key is trusted **for that Session only**: serve writes it to a known-hosts file of its own (`quick_known_hosts`, in the askpass channel's user-only directory, removed when serve exits) under a one-off `HostKeyAlias`, and ssh runs with `StrictHostKeyChecking=yes`, that file as its only `UserKnownHostsFile`, no global file, `UpdateHostKeys=no` and `ControlPath=none`. So a key that changes between the question and ssh's own connection is refused by ssh, one Quick Connect's key is never trusted for another, and nothing is added to `~/.ssh/roster_known_hosts`: a box nobody added doesn't become trusted for a Host added later at that address (ticket 15's "Save to vault" records it, after the login succeeded, Q43). That's the key the user confirmed for the Session, kept by serve with the Quick Connect, not a new scan: so the key the new Host is trusted with is the one ssh checked strictly when it logged in.

- **Shell hooks** (ticket 121, decision Q130) are the one place roster types into a Session by itself, and only when `shell_hooks` turns them on: a fixed line built into the app (no Host, Config or Plugin text goes into it, no secret), sent once at an empty prompt before the user types, never written to a file on the Host. A Host can fake a prompt to get it sent; all it gets is that public line run in its own shell. No Plugin can send it or anything else (`:integrate` isn't a command a Plugin may run).

## Config

`init.lua` is the user's own code. It runs in the Rust core, which never holds a secret, with no access to `roster serve`'s vault. It can choose a Login *reference* or a Host, never read a password.

Its `vault` table reaches `roster serve` through `vault.configure` (tickets 35, 41), and only as paths and choices: where "Save to vault" puts new items, and a KeePassXC database and key file. The schema has no other keys, and `serve` refuses any key it doesn't list, so nothing else, a secret above all, can ride along. Pointing at another database forgets the master password `serve` held for the old one, so it's never tried against a file it wasn't typed for.

It can't redirect a secret either. `roster_command` names the program that gets the master password, two-step codes and the API key's secret on its stdin, so init.lua may only name roster itself: `roster`, a path ending in `/roster`, or `uv run [--project <dir> | --directory <dir> | --frozen | --locked | --offline | --no-sync | -q] roster` (no `--with`, no other program). Anything else is a Config error, and starting the backend refuses it too. A wrapper needs the `ROSTER_APP_ROSTER` env var, which only the user sets, outside the Config. `:info` shows the command in use. The Lua sandbox has no `io`, so a Config can't write a program of its own to point at.

## Plugins

A Plugin is third-party Lua (decision Q81, [plugins.md](../plugins.md)). It runs in roster-core, in the same sandbox as `init.lua`, on a thread of its own with a memory limit and a time budget per call, and the core gives it only the functions for the permissions the user granted: without `terminal.read` there's no `terminal_output` event, without `inventory.read` no `roster.inventory`. Every function checks its grant again when it's called.

- **No secret ever reaches one.** The core holds none; a Plugin reaches roster only through `roster serve`'s methods its permissions name, from an allow-list that leaves out everything touching a password, a vault session or askpass (`vault.*`, `session.*`, `quick.*`, `host.add`, `host.save_login`, `changes.publish`). A manifest that asks for one doesn't install. Nor does one learn how a secret is fetched: a `cmd:COMMAND` or `env:VAR` Login reference reaches it cut to `cmd:` or `env:`, in every roster serve answer it gets, and in serve's error messages (decision Q92), since a secret pasted into a `cmd:` line would otherwise show. That's every text in the answer, not only an `auth`: raw text such as `changes.diff`'s diff of `roster.yml` and `host.check`'s step messages shows a reference as written, so the core cuts a `cmd:` one to the end of its line and an `env:` one's variable name wherever one starts a word (ticket 86). The app's own Pending changes and Health pages still show the whole diff and messages: only a Plugin's copy is cut. The same cut goes over the `job_progress` event, which is serve's own `job.progress` (a failed job's error message echoes the Login it was given), and over an answer's keys as well as its values. The CLI's `--json` output is cut by the same rule, on the output made plain JSON first, so a key or a value that isn't a string (a set, a path) can't carry one past it ([Machine-readable output](../cli-reference.md#machine-readable-output)). A test walks every function of the module with every permission granted and checks that roster serve only ever hears allowed methods.
- **What it can read.** `terminal.read` gets what Sessions print, never what's typed into them. A password typed at a prompt that echoes it would be in that output, and the install prompt says so. askpass's passwords never go through a terminal, and a prompt fill types a vault password only at a prompt that doesn't echo, so it's never in that output ([Filling a password prompt](#filling-a-password-prompt)). With a shell's OSC 133 marks (Q121) it also gets `command_done` and a `kind` on each run of lines, read from the marks the shell prints: a hint from the Host, never a reason to hold back or drop a line, and the command line only once the shell runs it. roster never writes to a Session for this.
- **It can't Publish.** `inventory.write` gives `host.update`, `host.rename`, `host.move` and `host.review`, which only make Pending changes.
- **What acts waits for the user** (decision Q100). Every serve method the install prompt flags (everything but the reads: `mesh.apply`, `mesh.cut`, `host.check`, `discover.start`, `discover.add`, …) and `inventory.write`'s methods run only in a call the user started: never at load, on an event or from a timer. The rule is derived from the flag in `permission.rs` (`serve_user_only`), not listed, so a new `mesh.`/`discover.` method waits for the user unless it's made a read. A call the user started is one they chose: a command, a key, a row's or button's action, a finder item, a toolbar control, a question's answer. A finder's `items`, a `:check` section's `check`, a command's `complete`, a timer and a question's `cancel` run because another Plugin's question took its place are the app's (the core marks the first three; the app tells it for the last), so another Plugin's `roster.cmd("finder …")` can't hand one the user's call. The user's call carries one hop and no further (Q98, Q103, issue #183): the answer to a request made in it, and the Plugin's own command its `roster.cmd` runs from it, are still the user's call, but a request or a `roster.cmd` made in either isn't. The core marks a `cmd` op made in such a carried run (`"user": false`), and the app runs the Plugin's command that line names as the app's call (`plugin_call`'s `carried` says the first hop is one), so a Plugin can't keep the user's call alive by chaining its own commands, or by passing it between requests and command lines.
- **A failed call leaves nothing behind.** Its ops are dropped, and so is what it did in the core: the functions it replaced stay, its timers and commands go. One call can ask roster serve at most 100 times and wait 300 s in all, so it can't keep serve from the app.
- **It draws nothing itself.** It hands over data (rows, text, items) that the frontend checks and draws with roster's own components: no HTML, no script, no iframe. It can't bind a key in the terminal, take a key or command that's bound already, or hide one with a longer sequence. A key it binds runs its line through the same check as a button's, each time it's pressed, so a key can't run `:plugins grant …`, `:packages`, `:source` or another Plugin's command ([Command lines a Plugin may run](../plugin-api.md#command-lines-a-plugin-may-run)).
- **Asked, and revocable.** It installs only after a prompt that lists every permission with the risky ones explained; an update that wants a new one asks again; `:plugins` revokes at once. What was granted is kept in the State, which neither `init.lua` nor a Plugin can write.
- **The network is one site at a time** (`network:SITE`, decision Q97). A Plugin reaches the network only through `roster.http`, an HTTP client in roster-core (reqwest, rustls), never through the webview, whose CSP allows no connection anyway. The function isn't there without a `network:` grant, and each request is checked again against the sites granted, before anything is sent and at every redirect. Sites match exactly (scheme, name, port); `*.example.com` is the one wildcard, for the names under a domain; https unless `http://` is written. Every name is resolved by the core and refused if any address it gives is on this computer or a private, link-local, shared or otherwise non-public network, and the connection goes to exactly the addresses checked, so DNS rebinding can't point a site inside after the check. Such an address is reached only when the manifest lists the address itself, or the name as a private site. No cookie jar, no proxy but the user's own `plugin_proxy` (the environment's and the system's proxy settings are ignored, and none carries credentials), no `Referer`, no retries, no credentials of roster's (it has none to give); the Plugin's own headers go, minus `Host`, `Content-Length`, `Transfer-Encoding`, `Proxy-*` and the others that steer the connection, and `Authorization`/`Cookie` are dropped on a redirect to another site. Caps: 256 KB out, 1 MB back, 10 s to connect, 30 s in all, 4 requests at once per Plugin. Each Plugin has its own client and connections. The request doesn't block the Plugin's thread: the answer comes back to its Lua as a call of its own, with a call's budget, and what that call changes reaches the app as data like any other ops. The prompt flags every site and says plain http and private addresses out loud; an update that adds a site asks again.
- **Private sites, pins and the proxy** (decision Q116). `network:private:NAME` is a name that resolves inside the private network: the core resolves it, refuses it unless every address is private (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7; never loopback, link-local, multicast or public), and connects only to the addresses checked, so DNS rebinding can't point it outside or at this computer. A name a private site lists is judged only by the private sites, so a public wildcard or another port can't reach it, and one manifest can't name it both ways. A public site is judged as before. `#sha256:FINGERPRINT` after an https site trusts exactly that certificate for exactly that site (scheme, name, port): a client of its own whose verifier accepts only that end certificate's SHA-256 for that server name, with the handshake signature still checked against the certificate's key (rustls's own check), and nothing else trusted; no redirect leads to a pinned site or from it to another, so the pin never replaces OS trust anywhere else and OS trust never stands in for a pin. `plugin_proxy` is the user's (init.lua), never a Plugin's: `http://HOST:PORT` only, refused with a user or password (and the error doesn't repeat it), and `Proxy-*` headers stay roster's to set, so nothing sends a proxy credentials. Only requests to public names go through it; private sites and addresses go direct. Through the proxy, the core still resolves a public name first and refuses it, exactly as without a proxy, if any address is non-public, at the first request and at every redirect; only when local resolution fails outright (a network where only the proxy resolves names) does the request go to the proxy unchecked. That residual case, and the moment between roster's lookup and the proxy's, leave the proxy to decide where the name leads: the option's docs say so. Each Plugin is handed its proxy setting when it loads, and a Config reload changes it for the running ones; their next request uses it. `:plugins` shows each granted site's request counts (sent, with no answer, when the last went), kept in the core per Plugin for the app's run and forgotten when it's removed (a request stopped by an unload counts as one with no answer): never a path, query, header or body.
- **Its folders are its own** (decision Q93). Every file of its code (manifest, `init.lua`, each `require`d module) is read only if its real path, after symlinks and Windows junctions, is inside the Plugin's folder, for local Plugins and Packages alike, so a link can't feed it code (or point it at a file) from elsewhere. Its data folder (`plugin-data/NAME`, next to the State, never the config folder, never on the network) is reached only through `roster.storage`, by plain file names: no paths, no `..`, no drive letters, no device names, and still no `io` or `os`. A link there (a symlink, or any Windows reparse point, junctions included) is never read, written or removed through, and a data folder that is itself a link isn't used; removing one removes only the link. Writes are atomic and capped (1 MB a file, 10 MB and 1,000 files a folder), so a Plugin can't fill the disk. It needs no permission: it reaches nothing but the Plugin's own files. The folder is removed with the Plugin (`:plugins remove`, `:packages clean`), never by a Plugin. `:plugins types` won't write the stubs through a link either.
- **Packages are fetched, never trusted.** A Package (a Plugin from a git repo, decision Q83) is cloned only when `init.lua` names it, into the app's own data folder, and runs only after the same prompt, with its git URL shown as unverified; Cancel deletes the clone. `roster.lock` pins its commit, and `:packages update` shows the diff and any new permission before moving it. git runs as a subprocess with no shell, no credentials from roster and no prompt for any, over `https`, `ssh` or `file` only (no `ext::`, no plain `http`), with no submodules and no hooks.

## Writes

- "Save to vault" saves only after the login succeeds (the add form's test login, or the Session's own login with that password), and refuses to create a duplicate Vault item name.
- The password it saves goes to `bw create item` as base64 JSON on stdin, never on a command line. bw's echo of the new item is read for its id only. Errors are cut from bw's stderr with the value removed.
- The undo after a failed add (`vault.undo_create`) can delete only items that this `roster serve` created itself, and Bitwarden keeps them in its trash.
- Publish never force-pushes.
