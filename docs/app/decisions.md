# Design decisions log (2026-10-29)

These came from a grilling session in which each question was asked with a recommended answer. The lasting, hard-to-reverse ones are also ADRs.

| # | Question | Decision |

| — | Is this worth building? | Yes as a team or personal tool. XPipe is the closest rival. The value is roster's model (team Inventory in git, per-service Logins, review gate, secrets kept from the UI), not "another SSH client". See [vision.md](vision.md). |

| Q36 | View modes | **Two modes** (simplified from three on 2026-10-29, so both can be done really well), toggled with `␣ m` or F11. `init.lua` picks the starting one.
1. **Standard**, the everyday layout: Sidebar tree A, title bar, optional status bar.
2. **Focus**: true OS fullscreen with no chrome at all. You get around like in Neovim: `␣ b` fuzzy-finds open Sessions (Telescope's buffer list), `␣ f` fuzzy-finds Hosts, and `␣ ]` / `␣ [` cycle Sessions.

**Every mode keeps all of roster:** the Picker, `:` command line, Quick Connect, Host details, the Key bindings panel, Lock, Inventory edits and Publish all work in every mode. Modes change how things are shown, never what you can do. What the Sidebar shows in Standard is reached through overlays and finders in Tmux and Focus. Prototype: `prototype-shell.html?mode=standard|focus`. Focus can optionally show the thin tmux-style session bar (`[box] 0:esxi-02* 1:…`): off by default, turned on with `focus.status_line = true` in `init.lua`. The Tmux mode, Compact rail and Mini window ideas were dropped. Split panes are still out of scope. *Q65 (issue #54): `␣ e` shows the Sidebar in Focus too, over the terminal; the tree finder is `␣ t`.* |
| Q37 | Your terminal config wins | **The terminal never fights the user's own setup.** Remote `.bashrc`, prompt, `LS_COLORS`, vim colour schemes and truecolor themes must render exactly as they do in any good terminal. The app sets `TERM=xterm-256color` and `COLORTERM=truecolor`, injects nothing else (no PS1, no sourced files, no output rewriting), and passes every escape sequence through. The 16-colour ANSI palette defaults to a neutral, standard one rather than the app accent. Themes and `init.lua` can change it, and a theme can say "leave the ANSI palette alone". |
| Q38 | Plugins and packages | **Neovim-style extensibility:**
- **Plugins** are Lua, run in the same runtime as the Config. They add commands, keys, themes, Sidebar sections, finder sources, status segments and event hooks.
- **Packages** are Plugins from git repos, listed in `init.lua` and pinned in `roster.lock` (lazy.nvim-style).
- The built-in features use the same registries.
- Plugins never see secrets, and their Inventory writes only become Pending changes.
- No plugin HTML/JS in v1.

See [ADR 0006](../adr/0006-lua-plugins-and-packages.md). Tickets 23–24, iteration 7. |
| Q39 | Per-mode layout | **Each view mode has its own layout table** in `init.lua`: which pieces show, where they go, and in what order. The pieces are the title bar, Sidebar (and its sections), session bar, status bar and its segments, and finders. For example, Focus can show the session bar at the bottom, and Standard can hide the status bar. Plugins can add pieces and segments to any mode. The defaults are the two modes as prototyped. |
| Q40 | No built-in vault | **The roster app will never have its own secret store.** Secrets stay in the user's password manager. The roster CLI and app only hold Login *references*, and never learn or keep a password beyond one lookup. Building a vault would mean owning encryption, recovery, sync, sharing and breach liability, and it would turn the product into the thing (Termius's vault) we set out to differ from. |
| Q41 | Local-only option | People without a team password manager get **local providers** instead of a vault: **KeePassXC** (`keepassxc-cli`, a local `.kdbx` file) is added, next to the existing `pass`. Both can read Logins and, like Bitwarden in ticket 13, create Vault items for "Save to vault". Ticket 25. |
| Q42 | Syncing your setup | `init.lua`, `roster.lock`, themes and personal Folders are plain files that sync through **git (dotfiles)**, the way the Inventory does. There's no vendor cloud. A `:config sync` helper that pulls and pushes that repo is a later proposal, not planned yet. |
| Q43 | Verified adds only | **A Host with a Login enters the Inventory, and a password enters the vault, only after a test login just succeeded with exactly those credentials.** That means the address was reachable, the host key was confirmed, and the user and password (or key) were accepted. This applies to the add-Host form (ticket 11), Quick Connect "Save to vault" (15), filling in `auth: prompt` Hosts (16), and changing a Host's Login in an edit (10). The order is always: verify, then create the Vault item, then add the Pending change. If the second step fails, the first is undone, so a failure leaves neither a stray Vault item nor a Pending change. Hosts *without* a Login (from `discover`) still enter as `reviewed: false` through the review gate. |
| Q44 | Clean errors everywhere | Every way a connection can fail, including entries made by hand in `roster.yml` or the vault, ends in a clean error with the Host, plain words, where the problem lives, the fix, and the raw message under Details. The catalog is `docs/app/errors.md`. `roster check HOST` / `:check HOST` run the diagnostics. A changed host key is never accepted automatically. Ticket 26, iteration 1. |
| Q45 | Live, two-way Inventory | Adding, removing and renaming **Hosts and groups** happens right in the Sidebar: `+` on a group heading, a row menu, `␣` keys and drag between groups. Each change writes `roster.yml` (comments kept) as a Pending change that you Publish (Q13). **Edits to `roster.yml` made outside the app show up in the Sidebar within a second**: `roster serve` watches the file, reloads it, and notifies the app. A file that doesn't load keeps the last good Inventory on screen with a clean error naming the line. Adding a Host with a Login still requires a successful test login first (Q43). Removing a Host asks for confirmation and never touches the vault. Tickets 28 and 10–12. *Reloading became Neovim-style (Q58, owner 2026-10-30): outside edits apply on `:source`, or within a second with `auto_reload = true`.* |
| Q46 | Folders in a file | Folders move from the State file into **`folders.yml`** next to `init.lua`: plain data that both you and the app edit. The app writes it on every Folder change, and edits made outside the app show up live. The app never rewrites `init.lua`, because that file is code. Folders that `init.lua` defines are shown marked "from init.lua" and can only be changed there. This supersedes the storage part of Q34; Folders remain personal and never go into the Inventory. |

| Q63 | Mesh: Host-to-Host access from one Box | **roster runs on one Box and sets up Host-to-Host access itself (owner, 2026-10-30): no roster, vault or password on any other machine, nothing to install or update there.** *Inventory:* a group's `mesh: true` lets its Hosts reach each other both ways; it cascades (`defaults` → group → Host), so `mesh: true` in `defaults` meshes every group, including new ones from `discover`; `mesh: false` opts out; unreviewed Hosts never join. Top-level `links:` add one-way reach across groups and networks, Host or group to Host or group (`{ from: subnet-1, to: subnet-42 }`, `both: true` for two-way). Each Host logs in to a peer as **that peer's** configured user. *How:* `roster mesh` (plan with `--dry-run`, then apply; `roster setup` runs it for meshed groups) makes a key **on** each source Host (the private key never leaves it), installs it on its peers tagged `roster-mesh:<host>` with `from="<source IP>"` and no agent or X11 forwarding, copies the peers' recorded host keys into the source's `known_hosts` (strict checking), and writes an ssh config so `ssh <peer>` works and a `ROSTER.md` listing only that Host's peers for Claude there (imported from `~/.claude/CLAUDE.md` when Claude is installed). It never runs on its own: after a Publish, `sync` and the app say "mesh out of date" with a one-key apply. Apply goes one connection at a time (rate limiters). *Edges:* Hosts that can't take a key (`enroll: false`, appliances) stay in the mesh as password peers: ssh asks the person for the password, roster never copies a password to a Host, and `ROSTER.md` tells Claude to ask the user to log in. ESXi works both ways, with the key and config kept somewhere that survives a reboot, and `roster check` notices if they're lost. Links across networks are tested from the source ("orion-2 can't reach …:22") rather than assumed; a `via:` hop is later.
